01

The Problem That Created RAG in the First Place

Large language models hallucinate. Not occasionally — structurally. They are trained to produce fluent, coherent text, and when they don't know something, they produce fluent, coherent text anyway. The training objective doesn't distinguish between "I know this" and "I'm pattern-matching toward a plausible-sounding answer."

Retrieval-Augmented Generation was the fix. Instead of asking the model to recall facts from parametric memory (weights), you retrieve relevant documents at query time and inject them into the prompt as context. The model's job shifts from "remember this" to "read this and answer." That's a much more tractable problem.

Pure vector RAG was the first serious implementation of this idea, and it works well enough that most production RAG systems today are still pure vector. But as the problems people tried to solve with RAG got harder, the limitations of pure vector retrieval became impossible to ignore.

02

How Pure Vector RAG Works

The pipeline is conceptually simple:

  • Take your document corpus and chunk it into fixed-size text segments
  • Embed each chunk into a dense vector using a transformer encoder
  • Store those vectors in a vector index (FAISS, Pinecone, Weaviate, etc.)
  • At query time, embed the query using the same encoder
  • Find the top-k chunks whose vectors are closest to the query vector
  • Inject those chunks into the LLM prompt as context
  • Generate an answer

The mathematical operation at the core is nearest-neighbor search in high-dimensional space:

$$\text{Sim}(\mathbf{q}, \mathbf{d}) = \frac{\mathbf{q} \cdot \mathbf{d}}{|\mathbf{q}| |\mathbf{d}|}$$

You're asking: which stored vectors are geometrically closest to the query vector? The assumption is that semantic similarity in language maps to geometric proximity in embedding space. And for a huge class of queries, that assumption holds up remarkably well.

03

Where Pure Vector RAG Breaks

Failure 1 — Context Dilution When you retrieve the top-k chunks by similarity, you're retrieving k independent text fragments, each embedded in isolation. For complex queries that require synthesizing information across multiple concepts, the context becomes diluted — a pile of loosely related paragraphs rather than a structured body of knowledge. The LLM has to do all the connective reasoning itself, which is exactly the kind of task that produces hallucinations.
Failure 2 — Multi-hop Reasoning Consider: "What metrics improved as a result of applying quantization to transformer-based models?" The answer doesn't exist in any single chunk. It requires following a chain: Quantization → applied to → Transformer Models → benchmarked on → GLUE, Inference Latency. A vector index has no mechanism to represent or query that chain. The LLM has to infer it — which it sometimes gets right and sometimes hallucinates entirely.
Failure 3 — No Provenance When a pure vector RAG system answers a question, you can tell the user "this answer came from these k document chunks." But you can't tell them "this specific claim came from this specific source." In scientific research contexts, researchers need to know not just what the answer is, but exactly which papers support each claim.
Failure 4 — Static Index A FAISS index is a snapshot. When you add new documents, you add new vectors — but the semantic relationships between new and existing documents aren't captured anywhere. If a new paper contradicts an old one, the index doesn't know. Each document is an island.
Failure 5 — Exact Lookup Ask a pure vector RAG system "how many papers in this corpus use attention mechanisms?" and it will retrieve chunks about attention and ask the LLM to count. The LLM will guess. Vector similarity has no concept of counting, filtering, or aggregation.

04

What Hybrid RAG Adds

Hybrid RAG keeps the vector retrieval layer and adds a structured knowledge graph layer on top. The two systems run in parallel and their outputs are fused before being passed to the LLM.

FAISS
Handles semantic similarity search — finding document chunks that are conceptually related to the query.
Neo4j
Handles structured graph traversal — finding explicit, multi-hop relationship paths between entities.

The retrieval router decides how to weight each source based on the nature of the query. A fuzzy conceptual question leans on FAISS. A structured relational question leans on Neo4j. Most real queries use both.

05

How the Hybrid Solves Each Failure Mode

Context Dilution → Structured Subgraphs

Instead of injecting k disconnected text chunks, the hybrid system injects both text chunks and a structured subgraph of entity relationships. The LLM receives:

Vector context: [chunk about quantization] [chunk about DistilBERT]
Graph context:  DistilBERT -USES_METHOD-> Knowledge Distillation
                DistilBERT -USES_METHOD-> 8-bit Quantization
                8-bit Quantization -IMPROVES-> Inference Latency

Multi-hop Reasoning → Cypher Path Traversal

MATCH path = (m:Method)-[:APPLIED_TO*1..3]->(result:Metric)
WHERE m.name = "Quantization"
RETURN nodes(path), relationships(path)

This traverses up to 3 hops from the Quantization node and returns every metric reachable through that chain. The answer is computed deterministically — no LLM inference required for the traversal itself.

No Provenance → Edge-Level Source Tracking

Every edge in the knowledge graph stores a sources property — an array of document IDs the relationship was extracted from. When the system answers using a graph path, it can trace every relationship back to specific papers. Provenance is structural, not approximate.

Static Index → Idempotent Graph Merges

MERGE (s:Entity {name: triple.subject})
  ON MATCH SET s.mention_count = s.mention_count + 1
MERGE (s)-[r:RELATION {type: triple.predicate}]->(o)
  ON MATCH SET r.sources = r.sources + new_source_id

Existing nodes get their mention_count incremented. Existing edges get the new source appended. The graph evolves continuously — it's not a snapshot, it's a living structure.

Exact Lookup → Cypher Aggregation

MATCH (p:Paper)-[:USES_METHOD]->(:Method {name: "Attention"})
RETURN count(p)

Exact, deterministic, no hallucination possible.

06

The Tradeoffs You Actually Pay

Hybrid RAG is not strictly better than pure vector RAG. It comes with real costs:

Complexity You're now operating two databases, two retrieval pipelines, a routing layer, and a fusion layer. Each has its own failure modes, operational overhead, and tuning parameters. A pure vector system is dramatically simpler to build, deploy, and debug.
Extraction Quality Dependency The knowledge graph is only as good as the triple extraction pipeline. If your NLP model extracts low-quality or incorrect triples, those errors are now structural — baked into the graph and influencing every query that touches those nodes. Bad graph triples produce confidently wrong reasoning.
Cold Start Problem A vector index is useful the moment you have documents. A knowledge graph needs enough entities and relationships to make traversal meaningful. A sparse graph with 50 nodes produces worse results than pure vector retrieval. The graph needs to reach a critical mass before the traversal advantage kicks in.
Latency Two retrieval systems running in parallel adds latency. A Cypher traversal on a large graph can be slow if indexes aren't properly configured. Pure vector search on a well-tuned FAISS index is extremely fast.

07

When to Use Each

Pure Vector RAG
  • Queries are primarily semantic ("explain X", "summarize Y")
  • Corpus is small and homogeneous
  • Need to ship fast, low operational complexity
  • Documents don't have strong relational structure
  • Approximate answers are acceptable
Hybrid RAG
  • Queries require multi-hop reasoning
  • Need fine-grained provenance at the claim level
  • Corpus is large, heterogeneous, continuously growing
  • Need exact aggregation queries
  • Hallucination on relational facts is unacceptable

08

The Core Insight

Pure vector RAG treats knowledge as a bag of semantically similar text fragments. Hybrid RAG treats knowledge as a structured graph of typed entities connected by explicit, directional relationships — with vector search as the entry point into that graph.

Bottom Line The question isn't which is better in the abstract. It's whether your problem requires the structural reasoning that only a graph can provide. For general Q&A over a document corpus, pure vector is probably sufficient. For a system that needs to reason about how concepts relate to each other across hundreds of papers — like this research agent — the graph layer isn't optional. It's the entire point.
